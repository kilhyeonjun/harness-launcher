# Formal canonical bootstrap execution plan

## Scope and acceptance

Break the sealed-verifier bootstrap cycle with the existing transaction engine,
source-admitted launcher activation and genuine native main-TUI exact once
approval. The public launcher owns the entry, protocol and release pin, not the
private engine implementation. Preserve registered root, origin, publication,
owner, occupancy, operation locks, config digest and old-verifier boundaries.

The command accepts only `--profile`, `--expected-base` and `--revision`.
Release-owned source and native tuples are not caller overrides. CLI input,
fixture approval and operation identifiers never confer approval. No existing
authentication or history is copied into the fresh operation home. Cancellation,
drain and uncertainty must remain distinguishable from successful application.
Existing project workspaces, sessions and installed older releases remain intact.

Generic MCP transport changes, provider implementation, authentication changes,
Git configuration changes and policy relaxation are excluded. This bootstrap
release does not depend on a future compatible MCP upstream release.

## Implementation and interfaces

1. `bin/harness-canonical-update` invokes `harness_canonical_bootstrap.py`.
   The controller admits the installed release and exact private closure before
   starting the pinned native runtime with `omp_canonical_bootstrap.mjs`.
2. `bin/canonical-bootstrap-source.json` binds the officially delivered private
   revision, exact manifest digest and seven file tuples to the original native
   version, source revision, byte count and binary digest. Private source is
   staged by the existing admitted activation path, not vendored publicly.
3. Preserve whole-operation lease custody. An independent observer validates
   actual kernel process and lock ownership. A bounded socket protocol binds the
   native operation; a separate FIFO can invalidate but never approve it.
4. Only genuine native literal once consent permits the unchanged engine's
   apply path. Preserve the exact scope, expiry, rechecks, truthful outcomes and
   cleanup/drain semantics. Never reopen the lease inode through another handle.

## Verification and release gates

- Python behavior regressions cover custody, source admission, tampering,
  selection continuity, expiry and process identity. Node behavior regressions
  cover approval protocol, denial, cancellation, lifecycle and result bounds.
  Register both through the existing full runner and its CI inventory.
- Exercise the original pinned native UI in a disposable operation. Synthetic
  cancellation or denial smoke proves only that bounded path, not real engine
  application, installation or human once approval. Never send approval keys in
  automated smoke.
- Validate the real release pin against the official private delivery and push
  acknowledgments, canonical manifest bytes and exact file rows. Run shell
  syntax and public documentation checks.
- Publish a reviewed pull request. Require all genuine CI partitions and their
  source/inventory coverage aggregate; missing, skipped or failed required
  partitions are not successful verification. Preserve any local full-suite
  timeout as a limitation rather than weakening the runner.
- Release from reviewed clean main, publish the official tag and GitHub release,
  and update the versioned Homebrew formula together with the command symlink
  and guide installation. Do not export this command from an older payload.
- Use the existing admitted activation route to install the public release and
  exact private closure. Verify immutable installation and staging receipts,
  retained older releases and sessions, and the actual installed command path.
- Return the exact installed approval-surface command with release/source
  receipts. The owning profile rechecks its actual target and base immediately
  before the human's exact once decision. No cross-profile source or credential
  adoption is part of this handoff.

## Native OS-account correction

The pinned 18.11.3 runtime's `userInfo().homedir` follows the deliberately fresh
native HOME. It cannot be the source of OS-account authority. Keep fresh HOME
and all source/tree/native/frame/observer checks; replace only this lookup.

- Reuse literal `/usr/bin/python3 -I -S -B -c` and a fixed UID/passwd script;
  no shell, caller arguments, path discovery or target-tree helper. Use cwd `/`,
  PATH-only `/usr/bin:/bin`, ignored stdin/stderr, byte stdout, 15-second timeout,
  SIGKILL timeout termination and a 4096-byte cap.
- Require successful unsignaled status, canonical compact UTF-8 closed
  `{home,uid}` bytes, exact native UID and an absolute normalized physical
  owner-safe home. Reject malformed/duplicate/extra fields, alternate encodings,
  failures and unsafe ancestry. Never fall back to environment or control data.
- Preserve the actual failure's unknown/cleanup result; no automatic replay.
  The owning profile reconciles its old process/lease/canonical state separately.
- Prove the unmodified getter under the original pinned native with fresh HOME,
  then admit the common public/private trees. No substituted getter/interpreter,
  company/profile records, approval keys or engine execution. After normal new
  release/install, test the actual installed startup's source-admission boundary
  separately before any owner-authorized operation. A read-only source check is
  not BIND, native approval, engine success or genuine HUMAN once.

## Evidence boundaries

Code review, fixtures, a published pin and private delivery do not prove public
CI, release, installation, real engine execution or human approval. Track these
as separate gates. Report the actual observed review model or mark it unverified;
never silently substitute a provider or treat a capacity failure as approval.
